# Cx1ClientGo Examples

Three kinds of documents live here, each answering a different question:

- **Confused about object ordering/dependencies?** Read
  [`OBJECT_MODEL.md`](OBJECT_MODEL.md) — platform object relationships
  and required sequencing. No code, prose/diagram only.
- **Trying to accomplish a specific task?** Read
  [`RECIPES.md`](RECIPES.md) — generalized, realistic task patterns
  ("get from zero to done"), one runnable example per pattern.
- **Trying to understand one API mechanic in isolation?** See the
  concept demos below.

## Concept demos

Each of these isolates a single API mechanic, written to make that
mechanic clear rather than to reflect a realistic call site:

- **AccessManagement**: show current user's ast-scanner role authorizations, create a new OIDC client with tenant-level ast-scanner auth, connect with that client and show its authorizations, delete the client.
- **ListScans**: take a user-supplied set of filters and fetch the list of scans matching the filter, outputting in a |-delimited format to the console.
- **MigrationImport**: using an extract from CxSAST (zip file) + decryption key, upload the file to Cx1 for import and poll until completed.
- **OneHundredApps**: create 100 groups, applications, and projects. for each tuple, assign the project to the application, assign the group to the project, and run a github.com-sourced scan in the project.
- **QueryManipulation**: create or find an existing "test-application" application with a "test-project" inside the application. retrieve the last completed scan for that project, or else run a new scan from a git repo. using that scan (if successful) create a SAST audit session. Using that session, retrieve the list of all queries, and print out the custom queries that exist in the environment. Create query overrides on the Tenant, Application, and Project level, create a new tenant-level query, and then run an invalid (broken) query followed by a valid query. Show the results generated by the query. Repeat a similar process of creating overrides & new tenant-level query for the KICS/IAC engine.
- **Reporting**: create a project with no Application at all, run a scan with multiple engines enabled, then request/poll/download scan-level and project-level reports via both the v1 and v2 report APIs. Also covers the separate SCA SBOM export cycle, and re-using a downloaded SBOM as the source for a new scan instead of a git repo or archive.

## Task recipes

Each of these is a realistic, third-party-plausible script covering a
whole task end to end. See [`RECIPES.md`](RECIPES.md) for the full
write-up (problem solved, when to reach for it) of each:

- **recipes/scanandtriage**: get or create a project, reuse its latest completed scan or trigger and poll a new one, then triage a SAST finding with a comment.
- **recipes/provisionteam**: idempotently provision an Application + Group hierarchy with role bindings and access grants for a new team, plus a matching concurrent bulk teardown.
- **recipes/enrichandexport**: list all projects, resolve each one's SCM repository and application via a memoized cache, export a CSV report.
- **recipes/whocanaccess**: resolve everyone with effective access to a resource, recursively walking group membership trees.
- **recipes/scanhistorymetrics**: aggregate language usage across a large filtered scan history using the bulk-beyond-one-page fetch convention.
- **recipes/downloadfindingsources**: batch-download the source files behind a set of findings to a local mirrored directory tree, with dedup and throttling.

## Authentication options

`AccessManagement` shows the two most commonly needed constructors end to
end (default/env-based `NewClient`, and OAuth client-credentials via
`NewOAuthClient`), but the client supports a few more shapes for
authenticating — pick whichever matches how the credential was handed to
your script:

| Constructor | Use when you have... |
| --- | --- |
| `NewClient` | CLI flags for tenant, base URL, and either an API key or OAuth client ID+secret (auto-detected) — see AccessManagement |
| `NewOAuthClient` / `NewOAuthClientWithToken` | an OIDC client ID + secret directly (e.g. a service account created for the script) — see AccessManagement; the `WithToken` variant additionally accepts a still-valid access token to skip the first login round-trip |
| `NewAPIKeyClient` / `NewAPIKeyClientWithToken` | a Cx1 API key (refresh token) instead of a client ID/secret — the common shape for CI/service-account credentials |
| `NewTokenClient` | only a raw, already-issued access token (e.g. a zero-trust workflow that hands your script a short-lived token rather than a long-lived credential) |
| `NewClientWithOptions` | full manual control over every field of `Cx1ClientConfiguration` — all the constructors above are thin wrappers around this one |

All of them return the same `*Cx1Client`, so everything downstream (every
concept demo, recipe, and the object model) behaves identically regardless
of which constructor you used to get there.

## Error handling

Every failing API call returns a plain Go `error` — there is no typed
error struct or `.StatusCode` accessor to inspect. The message is
formatted as `"HTTP <status> <reason>: <server message>"` (see
`plumbing.go`), so the reliable way to branch on a specific HTTP status —
e.g. to treat "409 Conflict: already exists" as a success case during
idempotent provisioning — is a substring check:
`strings.Contains(err.Error(), "409")`. This is the pattern used in
`AccessManagement` and in `recipes/provisionteam`; don't assume a more
structured error type exists anywhere in the client.
